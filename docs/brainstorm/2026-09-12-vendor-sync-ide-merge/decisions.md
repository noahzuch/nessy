F-5: [verified] The problems the user wants the IDE approach to fix, in their words: (a) **human control** — see and resolve every conflict in a familiar visual tool instead of approving the agent's summaries; (b) **cost and speed** — the hunk-grouping dialogue is slow and token-hungry, most changes merge cleanly and only real conflicts need attention; (c) **observability** — "it is hard to know everything merged correctly without having a visual diff view of upstream to current and local to current". D-1: [accepted] **The human resolves the merge in the IDE; the agent orchestrates and reports.**
     - Evaluated: (a) human resolves, agent orchestrates — script stages the three versions and launches the IDE merge, the user resolves every conflict, the agent explains what upstream changed, waits, runs `--continue`; (b) agent pre-merges as today, then the result is opened in a 3-pane view for human review; (c) mechanical 3-way merge first, human only on conflicting files; (d) different split per case (`merge_needed` vs `base_missing`).

     - Rejected (c): clean hunks would land without anyone seeing them, reversing the "no default adoption" rule (F-7) and repeating the silent-mismerge risk of F-6 with nothing watching.
     - Rejected (d): deferred, not ruled out — how `base_missing` maps onto a 3-way tool is still open (see later entries).
     - Chosen because: it addresses all three drivers in F-5 at once — control (the human decides in the tool), speed (no per-hunk dialogue), observability (the 3-pane view is the review). The agent's remaining job is the one it does well: summarise upstream's intent and run the scripts.

Rejected option (c) is partially superseded by D-5's *symmetric mode*: the user may choose per merge that non-colliding upstream changes are applied and staged unseen; the difference to (c) as rejected here is that it is an explicit per-sync choice and nothing is committed unseen — the staged diff is the review.

F-12: [verified] **JetBrains CLI merge**: `idea merge <left> <right> [<base>] <output>`; in source (`MergeApplication.kt`) the panes are `left, base, right` = args `[0], [2], [1]`, titled "Your version" / "Base version" / "Changes from server", so local goes first, upstream second. The command blocks until the merge window closes (`runWhenWindowClosed`); exit 0 = Apply / Accept Left / Accept Right, exit 1 = Cancel, 127 = exception. On Cancel the output file is restored to its pre-merge content. Exactly one file per invocation; `idea diff <dir1> <dir2>` compares folders but offers no 3-way merge. When an IDE instance is already running, the second process connects to its socket and the merge opens *in the running instance*; the wait for the result is unbounded. Non-text input falls back to whole-file binary accept. (Source: research subagent; https://www.jetbrains.com/help/idea/command-line-merge-tool.html, `platform/diff-impl/.../MergeApplication.kt`, `DiffBundle.properties`)

F-15: [verified] `git mergetool` runs "on every file with merge conflicts" and cannot be pointed at arbitrary files: it requires unmerged index entries. F-16: [verified] `git merge-file` needs no repository: clean merge → exit 0; conflicts → exit = number of conflicts (capped at 127) with `<<<<<<< / ||||||| / ======= / >>>>>>>` markers under `--diff3`/`--zdiff3`; error → 255. It supports `-L` labels, `-p` to stdout and `--ours/--theirs/--union` auto-resolution. (Source: `git merge-file --help` and a run outside any repo by the research subagent)

F-17: [verified] **A genuine git conflict state can be fabricated without any merge in progress.** In a throwaway repo (git 2.50.1), feeding `git update-index --index-info` a stage-0 removal line (`0 <40 zeros>\t<path>`) followed by stage 1 (base), 2 (local), 3 (upstream) blob entries, then writing the working file with `git merge-file -p --diff3 …`, produces a state byte-identical (porcelain v2) to a real merge conflict for: `git status` ("Unmerged paths / both modified"), `git ls-files -u`, `git diff` (combined `diff --cc`), `--base/--ours/--theirs`, `git show :N:path`, `git checkout --ours/--theirs/--conflict=diff3/-m`, resolution via `git add`, abort via `git restore --staged --worktree <path>` or `git checkout HEAD -- <path>`, and the refusals of `git commit` ("unmerged files") and `git stash` ("needs merge"). Without the removal line, stage 0 survives and git shows a plain `modified`, not a conflict. (Source: spike in `scratchpad/spike-index-conflict`, helper `fabricate.sh`)

F-18: [verified] `git mergetool` runs against the fabricated state exactly as against a real conflict: it does not require `MERGE_HEAD`, passes correct `$LOCAL $BASE $REMOTE $MERGED` temp files (BASE = pinned upstream content), stages the result on success, leaves the usual `.orig` backup, and handles the add/delete cases with its normal "(c)reated or (d)eleted" / "(m)odified or (d)eleted" prompts. Add-only (stage 3 only) shows as "added by them", stage 1+2 as "deleted by them". (Source: same spike, steps 5 and 9)

F-19: [verified] Differences from a real merge: `git merge --abort` fails ("MERGE_HEAD missing") — abort must be `git restore --staged --worktree <dir>`; there is no `MERGE_MSG`, no "use git merge --abort" hint text, and the eventual commit is an ordinary single-parent commit. `git commit -a` commits files *with* markers — a footgun, but identical to real-merge behaviour. `git reset` (mixed) collapses the stages to HEAD while leaving the marker file in the worktree. (Source: same spike, step 8)

D-2: [accepted] **vendor-sync merges by fabricating a genuine git conflict state inside the vendored directory; the human resolves it with whatever tool reads git conflicts.**
     - Evaluated: (A) fabricated conflict state — auto-merge per file with `git merge-file`, write conflicting files as unmerged index entries (stages 1/2/3) with diff3 markers, `--continue` refuses while unmerged entries remain; (B) launcher per conflicted file — same auto-merge, conflicted files handed one by one to a configured `idea merge`/`code --merge` command writing into scratch, copied into the directory on `--continue`; (C) A plus an optional script flag that drives `git mergetool` over the unmerged files.
     - Rejected (B): needs per-IDE launcher configuration, opens one window per file sequentially, VS Code cannot signal cancel (F-14), users without a supported IDE get nothing; its one advantage — nothing touches the directory before the end — is outweighed by F-20: the IDE already shows the state natively.
     - Rejected (C): `git mergetool` works on the fabricated state anyway (F-18), so the flag adds surface to build and test for a behaviour the user already has by running `git mergetool` themselves; can be documented as a fallback instead of built.
     - Chosen because: IDE-agnostic by construction — every IDE's conflict UI, `git mergetool`, and plain editors all read the same index state (F-17, F-18, F-20); it opens in the already-running IDE with no launcher (F-10, F-20); the whole directory is presented at once; abort is a single `git restore --staged --worktree <dir>` (F-19); and the clean/conflict split gives the speed F-5(b) asks for while the 3-pane view supplies the observability of F-5(c). Supersedes the "never a mechanical merge, not even as a first pass" rule of the prior design (F-6) for this flow: the objection there was that nobody would see a silent mismerge; here the human reviews every file in the merge view and the staged diff (see Q-2, F-22).
     - Reading note: "`--continue` refuses while unmerged entries remain" was later refined to exit 1 (D-10); the separate `--merge` call mentioned in D-2…D-7 was folded into the start call by D-9 — read "`--merge`" in those entries as "the start call when it writes merge state".

F-24: [verified] The design uses no patch application. `git apply`'s failure modes from the first session (S1 F-14: atomic abort on one unpatchable hunk; hunks fail when a local file is deleted or its context moved) are properties of applying a *patch*. `git merge-file` merges three whole files by content and always yields an output — clean text or diff3 markers — with exit = conflict count; it has no "unpatchable" outcome and is invoked per file, so there is no cross-file atomicity. (Source: F-16, spike 1; S1 F-14 via subagent summary)

D-3: [superseded-by D-30] **Per-file case handling in `--merge`, mirroring what a real `git merge` leaves behind.**
     - Present in base, local and upstream, changed on both sides → `git merge-file`; clean → write + stage 0; conflicts → stages 1/2/3 + diff3 marker file.
     - Locally deleted, upstream modified → no merge call; write upstream's version to the worktree, stages 1+3 ("deleted by us").
     - Locally modified, upstream deleted → stages 1+2, local file stays ("deleted by them"; verified F-18).
     - Added on both sides, different content → stages 2+3 ("both added"; IDE shows an empty base pane).
     - Changed / added / deleted on one side only → write the result and stage it; no conflict entry.
     - Chosen because: these are exactly the states every IDE and `git mergetool` already know how to present (F-17, F-18, F-20); no new UI vocabulary is invented.
     - Caveat recorded: the "non-conflicting change adjacent to a conflict is auto-merged" behaviour (S1 F-12) is inherent to 3-way merging and remains; it is mitigated by the human reviewing the merged file in the 3-pane view and the staged diff (see D-2, F-22), not by avoiding the merge.

F-29: [verified] Insight, confirmed by the user: the trouble is a friction between git's **symmetric** conflict model (a conflict exists only where both sides touched the same thing; one-sided changes are applied unasked) and vendor-sync's **asymmetric** merge (local one-sided changes are trusted, upstream one-sided changes must be reviewed). Borrowing the unmerged index state as a review channel works where a file exists on both sides — the dialog shows all upstream changes as chevrons and local ones are bulk-accepted with "apply from left" (F-25) — and breaks at the edges where one side has nothing: git has no state for "new file, please review", only "added by them", which IDEs read as "you deleted it" (F-28). The deleted-locally-modified-upstream case is right only by coincidence: both models agree it needs a decision. Consequence: use the conflict state only where git's meaning and ours coincide; pick a different git state where they diverge. (Source: dialogue; F-25, F-27, F-28)

F-31: [verified] Content-based decline detection is not rigorous: git stores bytes, so an "empty" file saved with a UTF-8 BOM is 3 bytes, not the empty blob; IntelliJ's "ensure every saved file ends with a line break" can make an empty result 1 byte; and a reviewer may legitimately keep upstream's new file with emptied content, which is byte-identical to a decline. A placeholder text in the fabricated sides fails for binary files. Consequence: the accept/decline of a planned new file must be tracked by **index state** (present = accepted, absent = declined, otherwise undecided), never by content, which requires the IDE's decline action to remove the file rather than empty it. (Source: user objection; git semantics)

F-32: [verified] Clarifies F-30: the user closed the spike-4 merge window without choosing a resolution, so the decline path was simply not exercised; there is no evidence of the IDE failing to persist a resolution. The decline path for the empty-blob representation remains untested, and by F-31 it would not be relied on anyway. (Source: user statement)

D-5: [superseded-by D-35] **`--merge` offers two modes behind a switch; both share the start classification and the `--continue` gate "no unmerged entry remains in the directory".**
     - **Symmetric mode (git-native):** `git merge-file` per file; upstream changes that do not conflict are applied into the file without markers and the file is staged; only files with textual conflicts become unmerged (stages 1/2/3 + diff3 markers); new upstream files are written as **untracked** files. The reviewer inspects the directory's staged diff and unversioned files in the IDE as after an ordinary merge. Cheapest and most familiar; trades the per-change upstream review for speed.
     - **Asymmetric mode (vendor-sync's philosophy, D-4):** every file upstream changed becomes unmerged with stages 1/2/3 regardless of textual conflict, so the dialog shows one hundred percent of upstream changes as chevrons and local changes are bulk-accepted with "apply from left" (F-25). New upstream files use **stage 1 = empty blob, no stage 2, stage 3 = upstream** ("deleted by us" with an empty base), so Accept Theirs stages the content and Accept Yours removes the file — decision tracked by index state, never by content (F-31). The agent tells the user up front that in the IDE overview locally deleted files and upstream-added files look alike (F-27), and lists which paths are which.
     - Evaluated: untracked-only for new files in both modes (rejected for asymmetric mode: keeps the new file out of the Conflicts list the reviewer is working through); empty-blob base *and* local (rejected, F-31); stage-3-only (rejected, misleading grey marker F-28).

## Rejected Approaches
- **Empty-blob decline detection for new upstream files**: brittle under BOM / trailing-newline editor settings and indistinguishable from "keep the new file but empty" (F-31).
- **Placeholder text as fabricated base/local for new upstream files**: puts fake text into the dialog, turns an honest "added" marker into "modified", and cannot work for binary files (F-31).
- **Launcher-driven per-file merge (`idea merge` / `code --merge` on scratch copies)**: per-IDE launcher config, one window per file, VS Code has no cancel signal; superseded by the fact that IDEs read git conflict state natively (F-20). Reconsider only if an IDE turns out *not* to surface unmerged index entries.
- **Script-driven `git mergetool` flag**: redundant with the fabricated state, which `git mergetool` already consumes (F-18). Reconsider if users without an IDE ask for a guided walk-through.
- **Agent pre-merges, human reviews in the IDE** (D-1 option b): keeps the slow grouping dialogue and reviews an agent artifact rather than the sources.
- **Mechanical merge with clean hunks landing unreviewed** (D-1 option c): would reverse "no default adoption" and re-open the silent-mismerge risk; the chosen design instead stages clean merges for review before commit.
- **Keeping symmetric and asymmetric modes behind a switch** (D-5, D-14): asymmetric kept accruing special cases — the re-labelling pass, its rename setting, the path/directory write guard — each making the tool harder to predict (D-35). Reconsider only if per-change review of non-colliding upstream changes becomes a hard requirement again.
- **Fabricated local-as-base stages for the no-base case** (D-8, Q-10): its argument was asymmetric's selective-apply surface, which went with D-35; the empty-tree merge base is git's own answer (D-36).
- **Hand-rolled blob/index abort restore** (D-23's mechanism): loses file modes in both directions while reporting success (F-46, F-51); replaced by path-scoped git commands (D-27).
- **Patching only the forward writer's file writes** (D-28): fixed who wrote the bytes but left the classification hand-built, the source of forgotten cases (F-54); superseded by one `merge-tree` merge (D-30).
- **Branch-style temporary refs `refs/heads/vendor-*`** (D-37): advertised in `git branch`, and checking one out deletes every file outside the vendored directory (F-68); plain refs instead (D-38).
- **Keeping the base alive with a ref, re-pinning, or fetch-by-sha recovery**: no ref a clone fetches can hold it without pushing tags or branches (F-69, F-71, F-73); the base is stored in the tree instead (D-39).
- **Option B, the `git subtree --squash`-style chain** (Q-12): the chain is lost whenever a sync PR is squash- or rebase-landed (F-88, D-40). `git subtree` itself fails outright under squash landing (F-89). Reconsider only for repositories that land every PR as a merge commit.
- **A `git bundle` as the stored base**, alone or combined with B's chain: extra create/unbundle steps, no blob sharing (F-76, F-77); combined with the chain it restores the object but not the ancestry `git merge` needs, and `git merge --abort` deletes staged work outside the vendored directory (F-92, D-43).

- **Writing `MERGE_MSG` at the start**: the message would sit through the whole resolution and leak into unrelated commits (D-41); itself superseded when `--continue` began to commit (D-45).

F-76: [verified] Measurements and constraints for storing the base as a single archive instead of loose files (spikes `scratchpad/sz`, `scratchpad/bsize`):
     - **Storage is not the deciding factor.** 40 syncs of a 60-file, 720 KB tree: loose files `.git` = 192 KB, zip = 244 KB. Loose wins because unmodified base files are the *same blobs* as the vendored copies, while an archive is a fresh binary every sync — but ~27% at this scale, not the blow-up assumed earlier.
     - **Node cannot read a zip without help.** `node:zlib` handles raw deflate, but there is no built-in zip *container* reader. The scripts are dependency-free `.mjs`, so zip would mean shelling out to `unzip` — a new external tool on a core path.
     - **`git bundle` is the same idea without that cost**, but only in one specific form. `git bundle create <f> <sha>` fails ("Refusing to create empty bundle") because a bundle needs a **ref name**, not a bare sha. `--max-count=1` produces a 1.3 KB *thin* bundle that records the parent as a prerequisite and refuses to unbundle where that parent is absent — useless here, since absent history is the whole scenario. Bundling the ref without limits embedded all 40 commits (46 KB).
     - **The form that works:** synthesize a **parentless** commit over the vendored subtree (`git commit-tree <subtree>` with no `-p`), point a temp ref at it, bundle that. 2821 bytes, self-contained, and `git fetch <bundle> <ref>:<ref>` restored the **identical** subtree oid in a repo holding none of upstream's history. Read back with git alone.
     - Consequence: the orphan commit's sha differs from `manifest.sha` — it is a content carrier, not the pinned commit, so identity stays in the manifest and the F-75 tree-oid check remains the integrity mechanism.

F-77: [verified] There is no way to carry content to a clone without putting it in the worktree, and loose files can be made to behave much like an opaque blob (spike `scratchpad/attr`):
     - Everything in a commit's tree materialises on checkout, and the only refs a clone fetches are branches and tags. Tags travel on clone but are not pushed by default (F-73); an **orphan branch** would be ideal — content in history, nothing in the worktree — but branches are not pushed by default either, so a teammate's clone would not have it. Hence: worktree files, and the only open question is their format.
     - `.gitattributes` with `/.nessy/base/** -diff -merge linguist-generated` makes git render changes as `Binary files a/… and b/… differ` with a `Bin 11 -> 20 bytes` stat line — the diff noise is gone without the content being binary.
     - Blob sharing is real and exact: the stored base file and the vendored file with identical content resolved to **one** object (`f1b8ef5…` for both).
     - **ripgrep skips the dot-directory by default** (`rg -l` found only `vendored/a.md`; `--hidden` was needed to see the stored base), and ripgrep is what most editors and agents search with. `git grep` and plain `grep -r` still find it.

F-78: [verified] How comparable tools solve the "where does the merge base come from" problem (web research, 2026-10-19). Three families:
     - **Store a reference, re-fetch on demand.** `git submodule` keeps a gitlink sha; **Copier** keeps `_commit` in `.copier-answers.yml` and **cruft** the equivalent in `.cruft.json`. Copier's update is our exact algorithm: check out the template at the recorded commit, regenerate what the project looked like then, diff against the current project, apply the new version. It therefore carries the same dependency vendor-sync has today — if the upstream repo loses that commit, the three-way merge cannot be performed. This is the mainstream answer.
     - **Embed upstream history.** `git subtree` merges the upstream commits into the consumer's own history, so the merge base is permanently local and `git merge` finds it with no bookkeeping. It is the only common tool that actually removes the retention dependency, and it pays with upstream's whole history in the consumer's log. Its `--squash` mode is the closest precedent to D-39: it records a **synthetic commit carrying upstream's tree** in the consumer's history instead of the real history.
     - **No merge at all.** `go mod vendor` and the npm family treat the vendored tree as pristine and store only integrity hashes (`go.sum`); local modification is not a supported workflow, so no base is ever needed.
     Vendor-sync sits in a gap none of them occupies: it wants local modifications (so it needs a base, unlike the third family) but not upstream's history (unlike subtree). D-39 — storing the base content without the history — is therefore unusual but has `git subtree --squash` as a partial precedent. The difference is that subtree can put its synthetic commit in the commit graph because subtree *creates commits*; vendor-sync deliberately leaves committing to the user, which is why its equivalent has to be files in the worktree.

F-79: [verified] How `git subtree --squash` handles local changes and later syncs, measured (spike `scratchpad/subtree`, `scratchpad/st2`):
     - `subtree add --squash` creates a **parentless commit whose tree is upstream's subdirectory** — the same object D-39 stores — and merges it into the consumer's branch as a second parent, recording `git-subtree-split: <upstream sha>` in its message. Later pulls chain onto it (`parents=[]`, then `parents=[<previous squash>]`).
     - Local modifications are nothing special: ordinary commits on the consumer's branch.
     - `subtree pull --squash` creates the next squash commit and merges it in. The merge base is the **previous squash commit**, reachable from the consumer's own history, so it is a genuine three-way merge: a local edit to line 2 and an upstream edit to line 8 merged silently, both preserved, no conflict. Collisions surface as ordinary git conflicts in the worktree.
     - **It does not depend on upstream retaining history.** With the old upstream commit expired from the reflog and gc'd out of the consumer, and upstream's history rewritten, `subtree pull --squash` still merged correctly from the locally stored squash chain.
     - The difference from vendor-sync is not the merge, which is the same three-way shape D-35 settled on, but the **commits**: subtree writes both the squash commit and the merge commit itself, and a clean merge is committed with no review step. Vendor-sync leaves committing to the user and stages the result for inspection instead, which is the gap it fills — and the reason its copy of the base has to be files rather than a commit.
